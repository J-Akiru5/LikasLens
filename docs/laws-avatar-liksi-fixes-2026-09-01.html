Part 2 — Avatar Reset Bug shipped

Reported Issue

Citizen (Jeff) uploaded a profile picture. It displayed correctly in the session but reverted to the default initial avatar after logging out and back in via Google OAuth.

Diagnosis: Both Hypotheses Confirmed

Hypothesis A — UX Flow Trap

confirmed

In profile/page.tsx, the onUploadComplete callback only called setAvatarUrl(url) — local React state. Persistence to Supabase required a separate "Save Profile" button click (handleSave, line 130). If the user uploaded a photo and saw the preview (local state), they assumed it was saved. It wasn't.

⚠ This is a UX trap regardless of Hypothesis B — photo upload reads as a completed action to users.

Hypothesis B — OAuth Identity Sync

confirmed

Even when handleSave() persists to user_metadata.avatar_url, Supabase's GoTrue server auto-populates this exact same field from Google OAuth provider data (avatar_url/picture claims) on every sign-in. The custom avatar is silently overwritten by Google's photo URL on the next login.

⚠ This is a platform behavior, not a bug in this app's code.

Fix (3 files changed)

1. Auto-save on upload (fixes Hypothesis A):

- onUploadComplete={(url) => setAvatarUrl(url)}
+ onUploadComplete={(url) => { setAvatarUrl(url); autoSaveAvatar(url); }}

New autoSaveAvatar function persists immediately to Supabase:

const autoSaveAvatar = async (url: string) => {
  const supabase = createClient();
  const { error } = await supabase.auth.updateUser({
    data: { custom_avatar_url: url },
  });
  if (error) showToast(error.message, "error");
  else showToast("Avatar saved", "success");
};

2. Custom avatar field (fixes Hypothesis B):

Custom avatars are now stored under user_metadata.custom_avatar_url instead of user_metadata.avatar_url. Google OAuth writes to avatar_url — it does not touch custom_avatar_url. No schema migration, no new table — just a differently-named key inside the existing user_metadata JSON field.

3. Read sites updated (all prefer custom_avatar_url with fallback):

FileChange
profile/page.tsx:80Load: custom_avatar_url ?? avatar_url ?? null
profile/page.tsx:155Save: writes to custom_avatar_url
user-nav.tsx:130Sidebar avatar: prefers custom_avatar_url
user-nav.tsx:171Header avatar: prefers custom_avatar_url
⚠ Architectural note: This is an app-level workaround for Supabase OAuth identity sync behavior, not a bug in this app's own code. GoTrue's default provider-identity sync is working as designed — it just collides with custom avatar storage under the same field name. The fix avoids changing GoTrue configuration (which would have broader auth implications).

Problem

Liksi answered "Tell me Liksi, what exactly is LikasLens? paano siya makakatulong sa akin?" with the file-a-report walkthrough instead of explaining what the platform is.

Root Cause

CITIZEN_SYSTEM_PROMPT's "Core Capabilities" list had no entry for explaining what LikasLens IS as a platform. Every capability was procedural: guide on filing, explain inspection, explain statutes. With no informational/onboarding capability, general "what is this" questions collapsed into the closest procedural match — the reporting walkthrough.

New capability added as the first entry in Core Capabilities (evaluated before procedural responses):

Platform onboarding & introduction NEW — answer FIRST

  • Only pivot to the step-by-step reporting walkthrough if the citizen's question is specifically about HOW to file a report, not WHAT the platform is.
