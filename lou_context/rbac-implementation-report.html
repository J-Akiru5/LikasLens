7. Final Architecture After Consolidation

Admin User/Role Management Flow

Browser (admin-portal)
  └─ users/page.tsx
       ├─ updateUserRole(id, role)   → fetch("/api/v1/admin/users/{id}/role")
       ├─ deleteAdminUser(id)        → fetch("/api/v1/admin/users/{id}")
       └─ bulkUserRole(ids, role)    → fetch("/api/v1/admin/users/bulk-role")
            │
            ▼
Next.js Proxy (admin-portal)
  ├─ /api/v1/admin/users/[id]/route.ts      (PUT + DELETE)
  ├─ /api/v1/admin/users/[id]/role/route.ts (PUT)
  └─ /api/v1/admin/users/bulk-role/route.ts (POST)
       │
       │  Reads Supabase session from cookies
       │  Forwards Bearer token to AI service
       ▼
FastAPI (AI Service - Render)
  └─ routers/admin.py
       ├─ PUT  /api/v1/admin/users/{id}       → require_super_admin
       ├─ PUT  /api/v1/admin/users/{id}/role  → require_super_admin
       ├─ POST /api/v1/admin/users/bulk-role  → require_super_admin
       └─ DELETE /api/v1/admin/users/{id}     → require_super_admin
            │
            │  JWT verified via JWKS
            │  role == "super_admin" enforced
            ▼
PostgreSQL (Supabase)
  └─ users table (via SQLAlchemy async)

Security Guarantees

  • Authentication: Supabase JWT (ES256) verified via JWKS at FastAPI layer
  • Authorization: require_super_admin dependency checks token["user_metadata"]["role"] == "super_admin"
  • No service-key exposure: Proxy reads session server-side, forwards Bearer token
  • No direct Supabase writes: All admin mutations route through FastAPI
  • Role validation: Endpoint validates role against allow-list before DB write
  • Audit logging: All admin actions logged with actor ID and target user ID
