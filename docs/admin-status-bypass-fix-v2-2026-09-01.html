3. Technical Decisions

3.1 Bulk vs Loop

Decision: Loop through single-ticket endpoint. Each of the 6 functions calls routeTicketStatus() which routes through PATCH /api/v1/ai/tickets/{id}/status. For bulk operations (bulkTicketStatus, escalatePattern), each ticket is validated independently in a loop. The server already has a bulk endpoint (POST /api/v1/tickets/bulk-status) but the client functions don't need it — looping reuses existing validated logic and is simpler. Admin bulk operations are small enough (5-20 tickets) that sequential requests are acceptable. Each failed ticket is tracked per-ID in a failed array.

3.2 urgency_score Handling

Decision: Passed in the same PATCH body. The existing StatusUpdateRequest on the server already accepts an optional urgency_score field. classifyTriageTicket and escalateTriageTicket pass it in the same request — no separate field update needed. The server applies both status and urgency_score in a single transaction before db.commit(), so they're atomic.

4. The Fix

4.1 New Helper: routeTicketStatus()

Extracted the routing pattern from updateTicketStatus into a reusable helper. All 6 functions now call this instead of writing directly to Supabase.

async function routeTicketStatus(
  id: string,
  status: string,
  extra?: { notes?: string; urgency_score?: number },
): Promise<ApiResponse<{ id: string; old_status: string; new_status: string }>> {
  // 1. Try authorized proxy: PATCH /api/v1/ai/tickets/{id}/status
  // 2. On failure: direct Supabase fallback (same as updateTicketStatus)
  // 3. Always: best-effort TicketTimeline entry in fallback path
}
