Result: Navigating to https://likasadmin.syntaxure.dev/ now redirects to /en instead of returning a 404. One line changed in the existing proxy middleware.

2. The Problem

The admin-portal's proxy middleware (src/proxy.ts) handled the root path / by calling NextResponse.next(), which passes the request through to Next.js. But there is no page.tsx at the app root — all pages live under [locale]/. So the pass-through hits no route and returns a 404.

Meanwhile, /en works perfectly — it matches the [locale] dynamic segment and renders the admin landing page.

Why no middleware.ts?

Next.js 16 uses proxy.ts as the middleware entry point (not the traditional middleware.ts). The admin-portal already had a fully-featured proxy.ts with Supabase auth session refresh, locale detection via next-intl, and login redirect logic — it just handled the root path incorrectly.

3. The Fix

File: apps/admin-portal/src/proxy.ts — 1 line changed

// Completely bypass for root path if (pathname === "/") { return NextResponse.next({ request }); }
// Redirect root path to default locale if (pathname === "/") { const url = request.nextUrl.clone(); url.pathname = `/${locales[0]}`; return NextResponse.redirect(url); }

locales[0] is "en" (from @likaslens/shared i18n config). The redirect is a 307 (temporary) by default, which is correct — it preserves the HTTP method and allows the browser to cache the redirect.
