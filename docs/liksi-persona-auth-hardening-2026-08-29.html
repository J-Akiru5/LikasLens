Liksi Persona/Auth Security Hardening

RECONCILED — 2026-08-29

TL;DR

A server-authoritative persona derivation fix was reviewed and approved across three cycles on feature/jeff/liksi-persona-auth-hardening, but never merged. A subsequent branch (feature/jeff/ai-route-adapters) reintroduced the vulnerability in three places. This report documents the regression and its reconciliation.

The Vulnerability

SECURITY The original route handlers trusted client-supplied context_mode and system_prompt fields. An unauthenticated user could:

  • Send context_mode: "admin" or context_mode: "lgu" to impersonate an officer
  • Inject an arbitrary system_prompt to override the AI's persona and instructions
  • The server would use these values directly without verifying the caller's identity

Timeline

~2026-08-28

feature/jeff/liksi-persona-auth-hardening created. Server-authoritative persona derivation: role derived from Supabase JWT, locale validated against allow-list, client context_mode/system_prompt never trusted. Reviewed and approved across three cycles. Never merged.

2026-08-29

feature/jeff/ai-route-adapters branched from development (before the fix). Created per-app route adapters (frontend, admin-portal, mobile-pwa) with correct architecture (createClient() from each app's own supabase util). However, because it branched before the security fix, it reintroduced the original vulnerability in all three new route files — now three instances instead of one.

2026-08-29

fix/reconcile-persona-auth-security created. Reapplied the approved fix from feature/jeff/liksi-persona-auth-hardening to all affected files. This is the second time this fix has needed re-establishing.

Root Cause

The fix was approved but never merged into development. When a later branch (ai-route-adapters) created new route handlers, it branched from the unfixed state of development. The new routes correctly used per-app createClient() (the architectural improvement), but inherited the vulnerable pattern of forwarding client-trusted context_mode/system_prompt.

This is the second time this fix has needed re-establishing — the first was the original review cycle itself. The pattern is: approved work sits unmerged, subsequent work branches from the unfixed state, vulnerability reappears.

What Was Fixed

Python (ai-service)

FileChange
routers/liksi.pyServer derives role from JWT user_metadata.role. LiksiChatRequest no longer accepts context_mode or system_prompt. Only locale is accepted (validated server-side).
services/liksi_service.pyAdded validate_locale() against allow-list (en, fil, vi, id, ms, ta, th). Unknown locales fall back to English. get_system_prompt() now takes locale parameter.
auth/supabase_jwt.pyReads JWT secret from centralized config.settings instead of os.environ.
config.pyNew centralized configuration module. All env vars loaded once via pydantic-settings.

TypeScript (shared + 3 apps)

FileChange
apps/shared/ai-gateway.tsRestored authToken and locale to ChatRequest. Restored apiKey to AIGatewayConfig. Gateway sends Authorization: Bearer <token> and X-API-Key headers. Strips authToken from JSON body before serializing.
frontend/.../chat/route.tsPasses session?.access_token as authToken. Forwards body.locale. No longer forwards body.context_mode or body.system_prompt. Adds apiKey to config.
admin-portal/.../chat/route.tsSame as frontend.
mobile-pwa/.../chat/route.tsSame as frontend.
All 3 health routesAdded apiKey to config (was missing — same regression pattern).

Lesson Learned

This is the second time this fix has needed re-establishing. The root cause is the same both times: approved work sits unmerged, subsequent work branches from the unfixed state. Merge security fixes immediately upon approval. Do not let them sit in review branches while other work continues.
