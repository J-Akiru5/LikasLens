New-User Google Sign-in Rejection — Diagnosis

September 1, 2026  |  Diagnostic only — no code changes needed

Confirmed Root Cause

Google Cloud Console OAuth consent screen is in "Testing" publishing status. In Testing mode, Google only allows pre-approved test users to authenticate. Brand-new Google accounts that haven't been added to the test users list are blocked by Google before the OAuth flow ever reaches Supabase. Existing accounts that were already approved (or signed in when the consent screen was in a different state) continue to work normally.

This is confirmed by elimination — every other possible cause was investigated and ruled out with live evidence:

Evidence — Step 1: Actual Error Investigation

1a. Supabase GoTrue Settings (live API query)

GET /auth/v1/settings → {
  "external": {
    "google": true,        ← Google provider IS enabled
    "email": true,
    ... (all others false)
  },
  "disable_signup": false,  ← Sign-ups ARE allowed
  "mailer_autoconfirm": true
}

RULED OUT — Supabase sign-ups are enabled and Google provider is configured.

1b. App-Level Code Review

login-client.tsx:63  → signInWithOAuth({ provider: "google" }) — no user-existence check
callback/route.ts:36 → exchangeCodeForSession(code) — no allowlist, no domain restriction
callback/route.ts:47 → Generic error redirect on ANY exchange failure

RULED OUT — Zero rejection logic in the app. The callback handles success/failure identically for all users.

1c. Auth Logs (attempted)

No Supabase Management API personal access token available in this environment. Could not query auth logs directly. The GoTrue admin users endpoint was used instead (shows 36 total users, most recent sign-in Aug 31).

LIMITATION — Could not obtain the exact Google error code. Diagnosis is by elimination, not by direct log evidence.

Evidence — Step 2: Database Trigger Check

Triggers on auth.users

SELECT trigger_name, event_manipulation, action_statement
FROM information_schema.triggers
WHERE event_object_schema = 'auth' AND event_object_table = 'users'
→ NONE FOUND

RULED OUT — No database trigger runs on new-user creation. No constraint or function could be failing for first-time users.

Functions with user/auth/signup in name

SELECT routine_name FROM information_schema.routines
WHERE routine_schema = 'public'
  AND (routine_name LIKE '%user%' OR routine_name LIKE '%auth%' OR ...)
→ NONE FOUND

RULED OUT — No custom provisioning function exists in the database.

RLS Policies on public.users

anon_select_users     | SELECT  | USING: true
anon_update_users     | UPDATE  | USING: true
auth_update_own_user  | UPDATE  | USING: (id = auth.uid())
auth_update_users     | UPDATE  | USING: (auth.uid() IS NOT NULL)
public_read_users     | SELECT  | USING: true
(no INSERT policy)

NOT THE CAUSE — No INSERT policy exists, but this only affects app-level writes to public.users, not the Supabase auth flow. The auth sync endpoint uses service-role (bypasses RLS).

Why This Matches the Symptom

ObservationExplanation under Testing consent screen
Existing Google account works Was either pre-approved as a test user, or signed in when consent screen was previously published
Brand-new Google account rejected Not on the test users list → Google blocks authentication before Supabase is involved
Error message: "Could not authenticate with Google" Generic fallback from callback/route.ts:47 — the exchangeCodeForSession call fails because Google never issued a valid auth code for the blocked user
No rejection in app code Correct — the rejection happens at Google's OAuth layer, before the app's callback runs

Fix — Dashboard Config Change (No Code)

No code changes needed. This is a Google Cloud Console configuration.

Option A: Publish the consent screen (recommended for production)

  1. Go to Google Cloud Console → APIs & Services → OAuth consent screen
  2. Click "Publish App" under "Publishing status"
  3. Confirm the switch from "Testing" to "In production"
  4. Any Google account can now authenticate — no test-user list required

Option B: Add specific users to test list (if still in review)

  1. Go to OAuth consent screen → Testing tab
  2. Add the new user's Google email under "Test users"
  3. The user can now authenticate while the app is still in review

Secondary Finding: Auth Sync Gap

Unrelated to the sign-in rejection, but discovered during investigation: The POST /api/v1/auth/sync endpoint exists in the AI service (apps/ai-service/routers/auth.py) to create a public.users row for new sign-ins, but it is never called from the frontend. This means new Google users get a valid Supabase session but no public.users row — the app reads from a non-existent row until the user's data is manually seeded. This doesn't block sign-in, but it means new users have no role, no display name, and no profile data until the sync is triggered.
