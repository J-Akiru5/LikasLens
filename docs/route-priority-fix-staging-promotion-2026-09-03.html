01 Executive Summary

A silent tiebreaker bug in route-to-office.ts caused ROLE_PRIORITY to be indexed by officerId (a UUID) instead of the officer's role string. Because a UUID never matches a key in { lgu_officer: 0, lgu: 1, analyst: 2 }, every lookup returned undefined, the ?? 3 fallback made every officer equal priority, and the sort became a no-op — producing non-deterministic assignment when multiple officers overlap on the same address token.

Impact Scope

main and staging are most affected: the admin-portal account-creation form on those branches uses a free-text service_area field with no coordinate capture, meaning every match goes through the broken text-fallback path. Two officers covering overlapping names (e.g. "Iloilo" and "Dingle") resolve arbitrarily instead of deterministically by role.

03 Root Cause Analysis

What is ROLE_PRIORITY?

const ROLE_PRIORITY: Record<string, number> = {
  lgu_officer: 0,   // highest priority — preferred desk
  lgu:         1,
  analyst:     2,   // lowest priority
};

The map is keyed by role string. A lookup like ROLE_PRIORITY["lgu_officer"] returns 0. A lookup with a UUID like ROLE_PRIORITY["a3f2...d91"] returns undefined, which the ?? 3 fallback coerces to 3 — making every officer equal and the sort order arbitrary (engine-dependent insertion order).

route-to-office.ts — BEFORE (broken sort keys)BUG

);
@@ textMatches sort @@
textMatches.sort((a, b) =>
- (ROLE_PRIORITY[a.officerId] ?? 3) - (ROLE_PRIORITY[b.officerId] ?? 3)
);

04 The Fix — Four-Hunk Patch

Two orthogonal parts: add role to OfficeMatch and populate it in both match paths; repoint the sort key from officerId to role.

Determinism Guarantee Post-Fix

When two officers overlap on the same address token, the sort now correctly orders: lgu_officer (0) < lgu (1) < analyst (2). The tiebreaker is now a true tiebreaker with a meaningful semantic.
