01 — start here

The blocker: new accounts can't be created at all

Reproduced live today against the deployed service. Any new user signing up — including any test account you create — fails at the sync step:

POST /api/v1/auth/sync
→ 500 NotNullViolationError: null value in column "password"
  of relation "users" violates not-null constraint

Why this looks like many bugs: the app keeps two user records — Supabase Auth (login) and the app's own users table (roles, permissions, ticket ownership). Sync creates the second one. When it fails, you can log in fine, but the backend has no row for you, so your role can't resolve. Every authorization check then fails, and every admin action looks independently broken.

The cause: the users table still has a password column marked NOT NULL — a leftover from the Laravel era, when that table handled passwords itself. Supabase Auth holds passwords now, so the app never writes one. The ORM doesn't model the column at all, so every insert omits it and Postgres rejects the row.

The fix is Jeff's, not yours — one schema change: make password nullable or drop it. Until that ships, testing new accounts will keep failing no matter what the UI does.

What to do meanwhile

Test with an account that already has a row in the users table with a role set — not a freshly created one. Ask Jeff which existing account to use. If your account predates this issue, you're fine; if you created it recently, that's very likely why everything 401s or 403s for you.

02 — not bugs

Three things that changed on purpose

These will look like regressions. They aren't — they're deliberate fixes from this week. Please don't file these.

The dashboard looks emptier, with fewer tiles

It used to show 5 KPI tiles including 840 total users, 42 active incidents, 17 ghost reports, +12% trend. Every one of those was hardcoded fake data — invented numbers that displayed regardless of what the database actually contained, including when a query failed outright. They're gone. It's now 3 tiles showing real counts. If the real count is zero, it shows zero. That's correct: showing fabricated metrics to competition judges on a platform whose entire pitch is evidence integrity was the single most dangerous thing in the codebase.

The Predictions page is missing from the nav

Deliberately hidden behind a feature flag defaulting OFF. There is no real forecasting model behind it — it would have shown synthetic trends from a handful of seed tickets labelled as predictions. Hidden until it's backed by something real.

Failed data loads now show errors instead of content

Previously, a failed or permission-denied query silently returned {success: true, data: []} — indistinguishable from "no data." Now failures surface as real errors. If you see more error states than before, that's the system telling the truth about failures it used to hide. Report what failed, but the error state itself is the fix working.

04 — status rules

Why some status changes are rejected

Status transitions are enforced server-side. A rejected change returns a real 422 with an explanatory message — that's correct behavior, not a bug. These are the actual allowed moves, read from the backend today:

open→ investigating, closed
investigating→ monitoring, resolved, closed
monitoring→ resolved, investigating, closed
resolved→ verified, closed
pending_review→ open, investigating, closed
verified→ closed
closed→ nothing (terminal)

The most common false bug report

open → resolved is not allowed — you must go through investigating first. If the UI offers "Resolved" as a button on an open ticket, that's a real UI bug worth filing (the buttons should reflect what's actually permitted), but the backend rejecting it is correct.
