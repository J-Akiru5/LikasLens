2. The Problem

Six functions in apps/shared/src/api/admin.ts wrote to tickets.status directly via Supabase, bypassing:

  • Transition validation — ALLOWED_TRANSITIONS state machine (e.g., closed → investigating is invalid)
  • Role enforcement — require_lgu_role middleware on the FastAPI endpoint
  • Audit trail — TicketTimeline row written for every authorized transition

One function was already correct:

  • updateTicketStatus() (line 160) → routes through PATCH /api/v1/ai/tickets/{id}/status — the reference implementation

3. The Fix

3.1 Approach

Category Functions Endpoint Used Reasoning
Single-ticket verifyReport, classifyTriageTicket, dismissTriageTicket, escalateTriageTicket PATCH /api/v1/ai/tickets/{id}/status Existing endpoint, already validated. Extended with optional urgency_score for compound writes.
Bulk bulkTicketStatus, escalatePattern POST /api/v1/ai/tickets/bulk-status (new) Each ticket validated independently. Entire batch rejected on any invalid transition. No partial application.

3.2 Server-Side Changes

1. Extended StatusUpdateRequest with optional urgency_score:

class StatusUpdateRequest(BaseModel): status: str notes: str | None = None
class StatusUpdateRequest(BaseModel): status: str notes: str | None = None urgency_score: float | None = None

2. Updated update_status() to apply urgency_score when provided:

3. New BulkStatusRequest model:

class BulkStatusRequest(BaseModel): ticket_ids: list[str] status: str notes: str | None = None

4. New POST /api/v1/tickets/bulk-status endpoint:

  • Fetches all requested tickets in one query
  • Validates each ticket's current status against ALLOWED_TRANSITIONS
  • If ANY ticket has an invalid transition → rejects entire batch with 422 + per-item error details
  • If all valid → applies transitions + writes TicketTimeline entries for each
  • Requires require_lgu_role (same as single-ticket endpoint)

3.3 Proxy Route

New file: apps/admin-portal/src/app/api/v1/ai/tickets/bulk-status/route.ts

Proxies POST requests to the AI service, forwarding the Supabase auth token. Same pattern as the existing [id]/status/route.ts proxy.

3.4 Client-Side Changes

File: apps/shared/src/api/admin.ts

Function Before (Direct Supabase) After (FastAPI Proxy)
bulkTicketStatus db().from("tickets").update({...}).in("id", ids) fetch("/api/v1/ai/tickets/bulk-status", {POST})

dismissTriageTicket db().from("tickets").update({status:"closed"}).eq("id", id) fetch("/api/v1/ai/tickets/{id}/status", {PATCH})
escalateTriageTicket db().from("tickets").update({urgency_score:5, status:"investigating"}).eq("id", id) fetch("/api/v1/ai/tickets/{id}/status", {PATCH + urgency_score:5})

3.5 Atomicity Note

For compound writes (classifyTriageTicket, escalateTriageTicket), the status transition and urgency_score update happen in a single FastAPI transaction via the PATCH endpoint. The two fields are updated together before db.commit(), so they are atomic within the database transaction. If the request fails mid-flight, neither field is persisted.
